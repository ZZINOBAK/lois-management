# Lois Management Agent Workflow

## Project
- Java 21
- Spring Boot 3.5.7
- Gradle
- MyBatis 3.0.5 (XML Mapper)
- MySQL
- Thymeleaf
- Spring Security

## Build & Test
- Build: ./gradlew build
- Test: ./gradlew test

## Architecture
- Controller → Service → Mapper 구조를 따른다.
- 기존 프로젝트 구조와 naming convention을 우선한다.
- 기존 기능의 동작을 임의로 변경하지 않는다.
- 기존 기능을 수정하거나 재현할 때는 새로 임의 구현하기 전에 기존 코드를 먼저 확인한다.
- 기존 비즈니스 로직을 재사용할 수 있는 경우 우선 재사용한다.
- 단, Demo 기능에서는 운영 DB 접근 여부를 확인하고 운영 데이터에 영향을 주는 코드를 그대로 재사용하지 않는다.

## Project Documentation
- 작업을 시작하기 전에 현재 작업과 관련된 `docs/` 문서를 확인한다.
- Demo 관련 작업에서는 반드시 `docs/demo-requirements.md`를 먼저 확인한다.
- 문서의 요구사항과 실제 코드가 다르거나 판단이 필요한 경우 임의로 결정하지 않고 사용자에게 보고한다.

## Workflow

### Planner
- 관련 문서와 기존 코드를 먼저 확인한다.
- 기존 기능을 수정하거나 Demo로 재현하는 경우 기존 구현과 변경 대상 구현을 실제 코드 기준으로 비교한다.
- 변경 범위, 대상 파일, 기존 기능 영향, 위험 요소, 테스트 방법을 포함한 Plan을 작성한다.
- 사용자 승인 전에는 파일을 수정하지 않는다.
- Plan은 구현에 필요한 결정사항 중심으로 간결하게 작성하고, 동일한 제약·영향·검증 내용을 항목마다 반복하지 않는다.

### Plan Reviewer
- 관련 문서, Planner가 작성한 Plan, 기존 운영 코드를 함께 검토한다.
- 파일을 직접 수정하지 않는다.
- 요구사항이 Plan에 빠짐없이 반영되었는지 확인한다.
- 기존 기능을 수정하거나 Demo로 재현하는 경우 실제 운영 구현과 Plan을 비교한다.
- Plan이 기존 기능을 임의로 단순화하거나 다른 동작으로 재설계하지 않았는지 확인한다.
- 운영 DB 접근, 인증/인가, 기존 기능 영향 등 위험 요소를 확인한다.
- 불필요한 리팩터링이나 작업 범위 확대가 포함되어 있는지 확인한다.
- 발견한 문제는 Critical / Major / Minor로 구분하여 보고한다.
- 문제가 있는 경우 직접 수정하지 않고 Plan 수정 방향을 제안한다.

### Implementer
- 관련 문서와 사용자가 승인한 Plan을 기준으로 구현한다.
- 승인된 범위를 임의로 확대하지 않는다.
- 기존 기능을 임의로 단순화하거나 다른 동작으로 재구현하지 않는다.
- Plan과 실제 코드가 충돌하거나 추가 변경이 필요하면 임의로 처리하지 않고 사용자에게 보고한다.

### Code Reviewer
- 관련 문서, 사용자가 승인한 Plan, 실제 구현 코드와 git diff를 함께 검토한다.
- 파일을 직접 수정하지 않는다.
- 구현 결과가 승인된 Plan과 요구사항을 충족하는지 확인한다.
- 승인된 범위를 벗어난 변경이 없는지 확인한다.
- 기존 기능의 의도하지 않은 변경이나 회귀가 없는지 확인한다.
- 기존 기능을 Demo로 재현한 경우 운영 구현과 Demo 구현을 비교하여
  기능, 비즈니스 규칙, 사용자 흐름이 임의로 변경되지 않았는지 확인한다.
- 운영 DB 접근, 인증/인가, CSRF 등 보안 또는 운영 데이터에 영향을 주는 변경을 확인한다.
- 테스트 결과와 테스트 누락 여부를 확인한다.
- 발견한 문제는 Critical / Major / Minor로 구분하여 보고한다.
- 문제를 직접 수정하지 않고 수정이 필요한 위치와 이유를 보고한다.

### Review Output Format
Plan Reviewer와 Code Reviewer는 리뷰 결과를 사용자가 빠르게 판단할 수 있도록 간결하게 작성한다.

- 발견한 문제는 Critical / Major / Minor로 구분한다.
- 각 문제는 다음 형식으로 최대 3줄로 작성한다.
  - 문제:
  - 왜 문제인지:
  - 수정 제안:
- 중복 설명, 긴 분석 과정, 불필요한 코드 전문은 제외한다.
- 이미 Plan이나 요구사항에 명시된 내용을 단순 반복하지 않는다.
- Critical과 Major는 발견된 문제를 모두 보고한다.
- Minor는 중요한 항목을 우선하여 최대 3건까지만 보고한다.
- 문제가 없으면 해당 등급은 생략한다.

## Safety / Rules
- DB schema 변경은 사용자 승인 없이 수행하지 않는다.
- 새로운 dependency는 사용자 승인 없이 추가하지 않는다.
- 배포 관련 설정은 사용자 승인 없이 변경하지 않는다.
- 인증/인가, CSRF, 운영 DB 접근 등 보안 또는 운영 데이터에 영향을 줄 수 있는 변경은 명시적으로 보고한다.
